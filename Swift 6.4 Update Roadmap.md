## Verification gates and version traps

- **SE-0532 is not available in the tested 6.4 SDK:** the September release announcement includes optional noncopyable improvements, but the August 31 implementation report assigns them to 6.5 and the proposal currently says accepted. Interface inspection and a minimal compiler probe confirm the absence of the proposed reference accessors in this distribution. Do not present them as shipped 6.4 APIs; see the validation record. [Release](https://www.swift.org/blog/swift-6.4-released/), [Implementation report](https://forums.swift.org/t/implementation-status-update-for-recent-language-and-library-proposals/89295), [Proposal](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0532-optional-noncopyable-improvements.md)
- **C++ span support has a checked return-path limitation:** E4's noescape const/mutable input overloads work without an experimental flag, but a default-empty Span traps in the generated conversion; the published boundary now handles empty input explicitly. Lifetimebound return overloads compile only in the tested experimental SafeInteropWrappers/LifetimeDependence configuration, whose runtime driver fails with signal 11 in both isolation settings. One isolated ASan diagnostic reaches the empty-tail case and reports stack-overflow during native sum. Keep those return examples compile-only; the stable owned-copy exercise passes. Exporting a native Swift Span parameter is also unrepresentable in the tested generated C++ header. [Release](https://www.swift.org/blog/swift-6.4-released/), [importer gating](https://github.com/swiftlang/swift/blob/main/lib/ClangImporter/SwiftifyDecl.cpp); see the validation record for the exact scope and unresolved cause.
- **SBOM generation and schema validation are different gates:** E5's real package produces CycloneDX 1.7/SPDX 3.0.1 JSON and correctly distinguishes an iOS-only dependency from a macOS build. This installed distribution warns that the SwiftPM_SBOMModel schema bundle is missing and skips schema validation. The record verifies contents, not schema conformance; local path package versions remain unknown. Standalone graph generation also warns that build-time conditions are absent. [SBOM guide](https://docs.swift.org/latest/documentation/packagemanagerdocs/generatingsboms)
- **Distribution validation must inspect diagnostics and launch consumers:** E7's ABI digester emits a frozen-layout break as warnings and returns zero despite -error-on-abi-breakage. Its initial default-Swift-Build binary consumer also builds/copies its framework but fails at launch because a matching runpath is absent; the native diagnostic control passes. The final root CLI manifest supplies @executable_path, and the default backend then builds and launches without manual copying or an environment override. These are checked local limits, not claims that every binary target fails. Only Swift 6.4/Xcode 27 and arm64 are validated.
- **Release highlights are not introduction dates:** module selectors are already marked implemented in 6.3. Also use the proposal spelling `@specialized`, checking it with the compiler; the 6.3 release overview spells it differently. [SE-0491](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0491-module-selectors.md), [SE-0460](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0460-specialized.md)
- **Observation proposal/API differences:** the tested SDK exports withContinuousObservation, not the proposal's withContinuousObservationTracking spelling. Its advanced APIs require Apple OS 27. A combined willSet/didSet/deinit registration emits the first mutation pair but no later deinit event on the tested runtime; a deinit-only registration does fire. F6 records both independent source/runtime discrepancies rather than promising the proposal example's later callback. [SE-0506](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0506-advanced-observation-tracking.md)
- **Accepted is not shipped:** exclude future-only features from baseline exercises. The implementation report places `withDeadline`, `Disconnected`, `FilePath`, noncopyable `reduce`, file-level defaults, and several other accepted changes in a later release; regex lookbehind and yielding accessors also need explicit status checks. Maintain a short deferred list instead of teaching proposal examples as available APIs. [Implementation report](https://forums.swift.org/t/implementation-status-update-for-recent-language-and-library-proposals/89295)
- **Implementation metadata can retain development flags:** check whether released 6.4 requires any flag for each example; do not copy an experimental flag just because it remains in proposal metadata.
- **Swift 6.4 compiler is not a new numeric language-mode setting:** record supported language-mode values from the compiler/SwiftPM, alongside tools version and SDK. Recheck inference under the actual target settings. A12 additionally verifies that `#if swift(>=6.4)` is true in mode 6 because it compares the effective language version; do not confuse that conditional with a valid command-line mode value.
- **API availability is separate from syntax support:** check runtime/deployment annotations for new library APIs. Building with Xcode 27 alone does not establish that a sample runs on every supported iOS/macOS version.
- **Testing interoperability is targeted:** F1 now verifies the installed Xcode XCTest separately from the Corelibs-focused proposal, including all four modes and tools-version 6.3/6.4 defaults. Do not imply all expectations, traits, UI testing, or performance APIs are interchangeable. [ST-0021](https://github.com/swiftlang/swift-evolution/blob/main/proposals/testing/0021-targeted-interoperability-swift-testing-and-xctest.md)
- **Test repetition summaries are not process status:** F1's repeat-until-pass fixture reruns only the failing case and eventually prints a passing summary, yet the tested SwiftPM command exits 1 after the earlier failure. Keep pipefail/raw status when formatting output; do not claim retries prove the defect fixed. [ST-0024](https://github.com/swiftlang/swift-evolution/blob/main/proposals/testing/0024-per-test-case-repetitions.md)

## Temporary example-validation workflow

1. Inventory Swift fences by note and section. Classify each as standalone runnable, type-check-only, multi-file/module, partial/pseudocode, expected diagnostic, expected trap, or platform-dependent.
2. Use an isolated temporary directory and explicit module-cache paths. Create temporary packages only for cases needing modules, tests, macros, resources, or C/C++ interop.
3. Record compiler build, SDK, deployment target, language mode, isolation policy, feature flags, and optimization mode for each version-sensitive result. Use Swift 6 language mode for the baseline; use Swift 5 mode only for a purposeful migration comparison.
4. Type-check or run all new/modified concrete probes and revisit every existing claim of exact compiler output or observed behavior. Use representative probes for unchanged fundamentals; do not claim all 1,953 fences are independent executable programs.
5. Check concurrency examples under both explicitly nonisolated and main-actor-default configurations where the distinction matters. Test ordering and cancellation deterministically; avoid proving behavior with timing guesses.
6. Separate expected failures from passing samples. Match the semantic diagnostic rather than unstable absolute paths or incidental wording. Run intentional traps in isolated processes with timeouts. Do not execute undefined-behavior examples as evidence of a language guarantee.
7. Validate Apple SDK examples against their documented availability. Add Linux checks only where practical and relevant; label untested platforms instead of claiming cross-platform verification.
8. Keep a Markdown validation record with note/section, command, environment, expected outcome, observed outcome, and limitations. Include enough source/context in the notes to recreate temporary probes later.
